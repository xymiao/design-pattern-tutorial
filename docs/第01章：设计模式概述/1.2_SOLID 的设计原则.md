# SOLID的设计原则

常用的面向对象设计原则 SOLID原则

这是五个原则的简写方式，分别是：

- 单一职责原则（SRP）
- 开闭原则（OCP）
- 里氏替换原则（LSP）
- 接口隔离原则（ISP）
- 依赖倒置原则（DIP）

## 1. 单一职责原则（SRP）

单一职责原则（Single Responsibility Principle）可以简写为：SRP。

### **核心思想**

- 一个类只负责一个功能领域中的相应职责，就一个类而言，应该只有一个引起它变化的原因。
- 每个类只负责单一功能领域。

### 代码示例

❌错误示范，**违反 SRP 的案例**

```java
class Order {
    // 订单相关属性 ...
    public void calculateTotal() { /* 计算订单金额 */ }
    public void saveToDatabase() { /* 数据库存储逻辑 */ }
    public void sendMessage() { /* 发送消息通知 */ }
}
```

✅正确示范，相对来说 **符合 SRP 的改进**。毕竟最后还是都要做到无招胜有招。

```java
class Order {
    // 只保留核心业务逻辑
    public void calculateTotal() { ... }
}

class OrderRepository {
    public void save(Order order) { ... }
}

class NotificationService {
    public void sendMessage(Order order) { ... }
}
```

### **实践技巧**

- 方法层面：每个方法只做一件事
- 类层面：类名应准确描述唯一职责
- 模块层面：使用包(package)组织相关类

## 2. 开闭原则（OCP）

开闭原则（Open Close Principle）可以简写为：OCP。

### 核心思想

- **对扩展开放，对修改关闭**
- 通过抽象和继承实现扩展

一个软件实体应当对扩展开放，对修改关闭。即软件实体应尽量在不修改原有代码的情况下进行扩展。

开闭原则的意思是：**对扩展开放，对修改关闭**。在程序需要进行拓展的时候，不能去修改原有的代码，实现一个热插拔的效果。简言之，是为了使程序的扩展性好，易于维护和升级。想要达到这样的效果，我们需要使用接口和抽象类，后面的具体设计中我们会提到这点。

### 代码示例

❌**违反 OCP 的案例**

```java
class DiscountCalculator {
    public double applyDiscount(String type, double price) {
        switch(type) {
            case "VIP": return price * 0.8;
            case "NEW_USER": return price * 0.9;
            default: return price;
        }
    }
}
```

**问题**：新增折扣类型需要修改已有代码

✅**符合 OCP 的改进**：

```java
interface DiscountStrategy {
    double apply(double price);
}

class VipDiscount implements DiscountStrategy {
    public double apply(double price) { return price * 0.8; }
}

class NewUserDiscount implements DiscountStrategy {
    public double apply(double price) { return price * 0.9; }
}

class DiscountCalculator {
    private DiscountStrategy strategy;
    
    public DiscountCalculator(DiscountStrategy strategy) {
        this.strategy = strategy;
    }
    
    public double calculate(double price) {
        return strategy.apply(price);
    }
}
```

### **实现方式**

- 策略模式（如示例）
- 模板方法模式
- 观察者模式

## 3. 里氏代换原则（LSP）

里氏代换原则（Liskov Substitution Principle）可以简写为：LSP

### 核心思想

- **替换性**：**子类对象应能无缝替换父类对象，且程序行为保持不变。**
- **行为契约**：子类必须遵循父类的方法约定（前置条件、后置条件、不变量），不可削弱或增强约束。

里氏替换原则（Liskov Substitution Principle, LSP）作为面向对象设计的核心原则之一，确立了继承关系的质量基准。该原则强调：程序中所有使用基类对象的位置，都必须能够透明地替换为其子类对象而不引发异常或破坏逻辑。这一原则的本质在于建立可靠的继承契约，要求子类必须保持与基类行为的一致性，同时允许扩展而非修改基类的功能。

LSP 是构建可持续复用架构的基石，其核心价值体现在两个方面：一方面保证基类可被安全复用，另一方面确保子类在遵循契约的前提下增强功能。这种约束有效避免了因继承滥用导致的系统脆弱性，确保类型层次结构具备真正的多态价值。

作为开闭原则的重要实践支撑，LSP 通过规范继承机制的具体实现方式，将"对扩展开放，对修改关闭"的设计理念落到实处。其实现关键在于严谨的抽象化过程——基类定义稳定的行为契约，子类通过实现契约的具体细节来实现扩展。这种分层抽象机制既保持了系统的稳定性，又为功能演进提供了明确的方向。

### **为何需要 LSP？**

- **避免意外行为**：若子类无法替代父类，继承层级可能引入隐藏错误。
- **维护抽象**：确保继承关系真正体现“IS-A”关系，而非仅代码复用的手段。

### 代码示例：

❌**违反 LSP 的案例**：

```java
class Rectangle {
    protected int width;
    protected int height;
    
    public void setWidth(int w) { width = w; }
    public void setHeight(int h) { height = h; }
    public int area() { return width * height; }
}

class Square extends Rectangle {
    @Override
    public void setWidth(int w) {
        super.setWidth(w);
        super.setHeight(w);
    }
    
    @Override
    public void setHeight(int h) {
        super.setWidth(h);
        super.setHeight(h);
    }
}

// 测试代码
void testArea(Rectangle r) {
    r.setWidth(5);
    r.setHeight(4);
    assert r.area() == 20; // 对于Square会失败
}
```

**问题**：Square修改了父类的行为语义



## 4. 接口隔离原则（ISP）

接口隔离原则（Interface Segregation Principle，ISP）：使用多个专门的接口，而不使用单一的总接口，即客户端不应该依赖那些它不需要的接口。

这个原则的意思是：使用多个隔离的接口，比使用单个接口要好。它还有另外一个意思是：降低类之间的耦合度。由此可见，其实设计模式就是从大型软件架构出发、便于升级和维护的软件设计思想，它强调降低依赖，降低耦合。

### 核心思想

- **客户端不应该被迫依赖它不使用的接口**
- 拆分臃肿接口为多个专用接口

### 代码示例

❌**违反 ISP 的案例**：

```java
interface Worker {
    void code(); // 代码
    void test();  // 测试
    void deploy();  // 部署
}

class Developer implements Worker {
    public void code() { ... }
    public void test() { /* 不相关实现 */ }
    public void deploy() { /* 空实现 */ }
}
```

✅ **符合 ISP 的改进**：

```java
interface Coder {
    void code();
}

interface Tester {
    void test();
}

interface DevOps {
    void deploy();
}

class Developer implements Coder { ... }
class QAEngineer implements Tester { ... }
class DevOpsEngineer implements DevOps { ... }
```

### **最佳实践**

- 接口方法数建议不超过5个
- 使用`default`方法提供默认实现
- 通过接口组合实现复杂功能

## 5. 依赖倒转（倒置）原则（DIP）

依赖倒转（倒置）原则（Dependency Inversion Principle，DIP）：抽象不应该依赖于细节，细节应该依赖于抽象。换言之，要针对接口编程，而不是针对实现编程。

这个原则是开闭原则的基础，具体内容：针对接口编程，依赖于抽象而不依赖于具体。

### 核心思想

- **高层模块不应依赖低层模块，二者都应依赖抽象**
- **抽象不应依赖细节，细节应依赖抽象**

### 代码示例

❌**违反 DIP 的案例**：

```java
class EmailService {
    public void sendEmail(String content) { ... }
}

class OrderProcessor {
    private EmailService emailService = new EmailService();
    
    public void process(Order order) {
        // 处理订单逻辑
        // ...
        //发送邮箱信息
        emailService.sendEmail("订单确认");
    }
}
```

**问题**：高层模块OrderProcessor直接依赖具体实现

✅**符合 DIP 的案例：**

```java
interface NotificationService {
    void send(String message);
}

class EmailService implements NotificationService {
    public void send(String message) { ... }
}

class OrderProcessor {
    private NotificationService notifier;
    
    // 依赖注入
    public OrderProcessor(NotificationService notifier) {
        this.notifier = notifier;
    }
    
    public void process(Order order) {
        // 处理订单逻辑
        notifier.send("订单确认");
    }
}
```

#### **实现方式**

- 依赖注入（构造函数注入、Setter注入）
- 使用Spring等IoC容器
- 工厂模式管理依赖



除了上面的五种常用的， 还有以下两种原则。 

**5、迪米特法则，又称最少知道原则（Demeter Principle）**

迪米特法则（Law of Demeter，LoD）：一个软件实体应当尽可能少地与其他实体发生相互作用。

最少知道原则是指：一个实体应当尽量少地与其他实体之间发生相互作用，使得系统功能模块相对独立。

**6、合成复用原则（Composite Reuse Principle）**

合成复用原则（Composite Reuse Principle，CRP）：尽量使用对象组合，而不是继承来达到复用的目的。

合成复用原则是指：尽量使用合成/聚合的方式，而不是使用继承。



# **SOLID原则综合应用案例**

**需求场景**

开发一个支持多种支付方式和日志记录方式的订单系统

代码示例：

```java
// 抽象定义
interface PaymentGateway {
    void processPayment(double amount);
}

interface Logger {
    void log(String message);
}

// 具体实现
class Alipay implements PaymentGateway { ... }
class WechatPay implements PaymentGateway { ... }

class FileLogger implements Logger { ... }
class DatabaseLogger implements Logger { ... }

// 高层模块
class OrderService {
    private final PaymentGateway payment;
    private final Logger logger;
    
    // 依赖注入
    public OrderService(PaymentGateway payment, Logger logger) {
        this.payment = payment;
        this.logger = logger;
    }
    
    public void checkout(Order order) {
        payment.processPayment(order.getTotal());
        logger.log("订单完成：" + order.getId());
    }
}
```

**原则对应分析**

1. **SRP**：每个类职责单一
2. **OCP**：新增支付/日志方式无需修改OrderService
3. **LSP**：不同支付方式可互相替换
4. **ISP**：接口职责明确
5. **DIP**：高层模块依赖抽象



# **常见误区与避免方法**

1. **过度设计**：
   - **表现**：在简单场景强制应用所有原则
   - **解决**：遵循YAGNI（You Ain't Gonna Need It）原则
2. **教条主义**：
   - **案例**：为每个方法创建独立接口
   - **平衡**：在灵活性与复杂度之间找到平衡点
3. **忽略上下文**：
   - **注意**：某些原则在特定场景需要权衡
     - 例如：性能关键代码可能需要违反DIP
